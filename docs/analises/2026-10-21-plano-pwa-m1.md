21/10/2026. Base inspecionada: `a5c683fa8df8296abaefdfae4e487a8c57d1ae1a`. Pedido atual: planejamento; sem mudança de runtime, instalação de dependências, publicação ou contratação. Decisões Q61–Q65 em [spec/14](../../specs/14-pwa-primeiro-marco.md); [pesquisa e fontes](2026-10-21-viabilidade-pwa.md); [tarefas locais](../../.scratch/pwa-m1/spec.md).

## 1. Recomendação e decisões

Adicionar um alvo web ao projeto Expo existente, começando por uma prova de portabilidade. Compartilhar domínio, contratos de sync, tokens e componentes compatíveis; separar armazenamento, sessão, ciclo de vida e foco. A primeira versão funcional será o M1, com o visual **Ritmo-App** e a mesma conta/API do nativo.

Expo oferece React Native Web para renderizar componentes no DOM e módulos específicos por plataforma. Isso sustenta a candidatura, sem comprovar que todos os imports atuais funcionam no Safari. [Expo Web](https://docs.expo.dev/workflow/web/), [módulos por plataforma](https://docs.expo.dev/router/advanced/platform-specific-modules/).

Abrir a URL no Safari e adicionar à Tela de Início são caminhos web, sem distribuição de binário na App Store. A preparação offline exige cache do código, banco, sessão, sync e atualização funcionando juntos. [Guia Apple](https://support.apple.com/en-lamr/guide/iphone/iphea86e5236/ios), [PWA no Expo](https://docs.expo.dev/guides/progressive-web-apps/).

## 3. Alternativas de frontend

| Opção | Ganho | Custo/risco | Posição |
|---|---|---|---|
| Expo Web + RNW no app atual | Aproveita componentes/tokens e uma base de produto | Imports nativos, DOM e adapters precisam de prova | Primeira candidata |
| React DOM separado | Liberdade para semântica/layout web | Segunda UI e evolução visual paralela; extrair domínio comum | Alternativa se houver impedimento relevante no RNW |
| Reconstrução integral/wrapper WebView | Não elimina contratos offline/sessão | Reimplementação ou distribuição nativa sem resolver a necessidade atual | Sem justificativa nesta etapa |

Não abrir monorepo novo, BaaS, microserviço ou refatoração ampla antes da prova. Interfaces pequenas podem entrar no próprio `app/`; extrair pacote só por necessidade concreta.

## 4. Persistência: primeira incerteza

Testar primeiro expo-sqlite web no SDK fixado pelo potencial de preservar schema/consultas. O suporte documentado é alpha e depende de WASM, SharedArrayBuffer e isolamento por headers; o pacote instalado usa OPFS. Isso não é aprovação para dados reais. [Expo SDK57 SQLite](https://docs.expo.dev/versions/v57.0.0/sdk/sqlite/); [inspeção e fontes](2026-10-21-viabilidade-pwa.md).

Comprovar transação intenção+projeção, migrations/PRAGMAs, persistência após reload/fechamento, worker sem bloquear UI, quota/falha sem sucesso falso e exclusão entre abas. Encapsular SQL síncrono numa Promise não remove o bloqueio da thread. Não remover uma garantia do adapter para fazer a prova passar.

Se falhar, avaliar IndexedDB com repositório assíncrono e transações explícitas. Isso afeta AccountStore/InstallationStore e consultas da Journey; não esconder promises atrás dos tipos síncronos atuais. Decidir após evidência, sem construir dois bancos de produto em paralelo.

Q63 não é backup. A solicitação de persistência pode ser recusada; servidor não reconstrói intenções nunca recebidas. Não programar exclusão/reset por quota, login ou atualização. Separar “salvo neste navegador” de “confirmado pelo servidor” na copy final a especificar.

## 5. Sessão web e API

Proposta: origem única HTTPS para frontend e fachada web de sessão na API Java existente, com cookie HttpOnly/Secure e proteção CSRF/Origin apropriada. Transporte nativo mantém contrato bearer. Não adicionar servidor Node apenas para a fachada sem necessidade demonstrada.

Uma sessão web no servidor permite manter refresh/revoke reutilizáveis fora do JavaScript. Ainda faltam expiração, rotação, perda de resposta, indisponibilidade e logout offline. HttpOnly reduz leitura da credencial por JS; não impede XSS de executar ações como usuário. [OWASP: sessão](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).

Session atual exige Credentials/SecureVault e cria HttpSync com bearer. Planejar fronteira de acesso remoto/sessão, preservar invariantes e testar nativo/web; não inventar cofre com localStorage. Fechar como o bloqueio local após logout offline impede uso indevido de cookie que JS não pode apagar.

WebKit documenta cópia inicial de cookies ao adicionar à Tela de Início, sem copiar os demais dados, e separação posterior. Não deixar a base nova usar acidentalmente a mesma família rotativa Safari. Recomenda-se reconhecer instalação nova e exigir autenticação online antes de vinculá-la a uma família própria, sem revogar a anterior por isso; mecanismo ainda pendente de contrato e prova. [WebKit/Safari17.2](https://webkit.org/blog/14787/webkit-features-in-safari-17-2/).

## 6. Cache, abas e atualização

O service worker prepara recursos estáticos para abertura; dados do usuário ficam no repositório local. Precache versionado de código/assets/fontes, sem respostas de autenticação/reset/sync tratadas como conteúdo público. SW não substitui outbox e não vira segundo escritor.

Sync em foreground, retomada e ação explícita, respeitando backoff. Não depender de timer com tela fechada ou background sync para garantir envio; notificações/push têm recorte próprio. [Limitações e fontes](2026-10-21-viabilidade-pwa.md).

Uma aba coordena escrita/sync/sessão; outras não fazem refresh, migrations ou comandos. Locks entre abas não coordenam os contêineres separados Safari/Tela de Início. Retomada invalida o proprietário antigo comprovadamente; timeout isolado não basta.

Atualizar sem reload forçado durante gravação. Fechar compatibilidade release/schema/protocolo e versões simultâneas antes do SW de produto. Não usar limpeza do site como procedimento normal. Expo destaca o risco de cache agressivo dificultar atualizações. [Guia PWA](https://docs.expo.dev/guides/progressive-web-apps/).

## 8. Infraestrutura e provas

Proposta: assets estáticos e fachada web/API pelo proxy HTTPS do ambiente existente. Hostnames são parâmetros pendentes; não reservar domínio/contratar VPS por este plano. Se houver origens distintas, especificar allowlist, credenciais e headers de erro/retry; não liberar `*` com cookies.

O ensaio pode usar origem HTTPS de teste autorizada, sem antecipar nome comercial. Localhost Windows e WebKit desktop não equivalem ao Safari do iPhone. IP local por HTTP não comprova capacidades de contexto seguro. [MDN: contextos seguros](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Secure_Contexts).

Para uso diário, continuam [domínio/DNS/Resend](../../.scratch/aceite-m1/issues/02-preparar-dominio-e-resend.md), parâmetros de recuperação e [validação operacional externa](../../.scratch/recuperacao-operacional/issues/04-validar-operacao-externa.md). Um hostname HTTPS fornecido pela hospedagem pode servir à prova se autorizado; não elimina gates de remetente e dados reais.

Aceite: executar WEB-01–10 e mapear M1-01–20, registrando iOS/Safari, instalação, build/origem e resultados. Capturas, VoiceOver e fluxo real no iPhone complementam automação desktop. Nenhum benchmark Android comprova desempenho Safari. Metas/medição web precisam ser consolidadas na tarefa02, sem enfraquecer silenciosamente as metas existentes.

## 9. Resultado desta etapa

Plano preparado; nenhuma PWA implementada/aceita. Q61–Q65 registradas no contrato canônico. Próximo recorte: **prova técnica web com dados sintéticos**, focando renderização e persistência no stack fixado. Exportar não decide banco nem sessão.

O [experimento nativo do checkmark](../../.scratch/interface-m1/checkmark-persistente.md) permanece no backlog.
